# Benchmark report — 2026-09-05, Linux x86-64

Everything below was produced by the code in this repository, on one machine, in one
sitting. Numbers that miss their gate are reported as missed.

## Machine

| | |
| --- | --- |
| CPU | Intel Xeon @ 2.60 GHz, **2 vCPU** (shared cloud sandbox) |
| RAM | 3 GiB |
| OS / kernel | Linux 6.1.158 x86-64 |
| rustc | 1.88.0, `--release` (opt-level 3, LTO fat, codegen-units 1) |
| WASM | `--profile wasm` (opt-level 2, LTO fat, panic=abort), 68 400 bytes, no SIMD |
| JS runtime | Node 22 / V8 — same engine class as Chrome |
| threads | **1** (the engine is single-threaded today; no rayon, no worker pool) |

Caveat worth stating plainly: this is a 2-vCPU shared VM, not a benchmarking rig. A
modern desktop core is typically 2–3× faster on this workload. Absolute numbers here are
a floor; the *ratios* between engines are the useful part.

## Corpus

`xmlspy gen` writes a PurchaseOrder document: 10 elements + 4 attributes per record,
UTF-8, with non-ASCII payload (`Zürich`) so the scanner cannot pretend the world is ASCII.

| file | size | records | elements | attributes | lines |
| --- | --- | --- | --- | --- | --- |
| `/tmp/po64.xml` | 64 MiB | 220 715 | 2 207 151 | 882 860 | 882 865 |
| `/tmp/po256.xml` | 256 MiB | 880 681 | 8 806 811 | 3 522 725 | 3 522 729 |

Generation itself: **997 MB/s** (64 MiB), **849 MB/s** (256 MiB).

## Scan + index throughput (single thread)

| engine | 64 MiB corpus | vs TypeScript |
| --- | --- | --- |
| Rust, native x86-64 (`xmlspy bench`) | **301 MB/s** | 4.6× |
| Rust → `wasm32-unknown-unknown`, in V8 | **252 MB/s** | 3.9× |
| TypeScript scanner (`src/engine/scanner.ts`) | 65 MB/s | 1.0× |

WASM retains **84 %** of native throughput. Enabling `simd128` (`SIMD=1 ./rust/build-wasm.sh`)
measured 233 MB/s — i.e. no gain, because the delimiter search is portable SWAR over `u64`
rather than explicit vector intrinsics; the baseline build is shipped so the module runs
on any WASM MVP browser.

`opt-level` matters far more than SIMD for this code:

| wasm `opt-level` | module size | throughput |
| --- | --- | --- |
| `"z"` | 57 981 B | 106 MB/s |
| `"s"` | 64 668 B | 190 MB/s |
| **`2` (shipped)** | **68 400 B** | **252 MB/s** |
| `3` | 72 550 B | 240 MB/s |

10 KB of module size buys 2.4× throughput, so the size-optimised profile was abandoned.

## 256 MiB run, native

| stage | result |
| --- | --- |
| well-formedness scan + index | 0.831 s — **323 MB/s** |
| index size (`max_indexed` = 300 000, the app default) | 20.30 MiB = **7.93 %** of the document |
| peak RSS during the scan | **74.7 MiB** (gate: < 512 MiB) — **PASS** |
| streaming literal search (`Zürich`, 146 780 hits) | 0.682 s — **394 MB/s** |
| full index, `max_indexed` unbounded | 0.976 s (275 MB/s), 286.40 MiB = **111.9 %** of the document, RSS 575 MiB |

The last row is the argument for capping the index: for element-dense XML (30 bytes per
element here) a complete structural index is *larger than the document*, at ~34 B/element.
The default cap keeps the index at 8 % of the file and the process under 75 MiB, which is
what makes the 1 GiB-in-the-browser story work.

## WASM boundary costs (V8)

| operation | cost |
| --- | --- |
| instantiate the 68 KB module (incl. base64 decode) | ~2 ms, once per thread |
| feed one 8 MiB chunk (copy JS → linear memory) | ~1 ms |
| decode the serialised `.xsi` into JS typed arrays, 490 715 indexed elements | 5–16 ms |
| streaming search, 64 MiB | 277 MB/s |

The index crosses the boundary exactly once, as a single `.xsi` buffer, and is decoded
into transferable typed arrays that are moved (not copied) to the main thread.

## Gates

| gate | target | measured | verdict |
| --- | --- | --- | --- |
| peak RSS, 256 MiB document | < 512 MiB | 74.7 MiB | **PASS** |
| index size vs document | < 10 % | 7.93 % | **PASS** |
| WASM module size | < 250 KB | 68.4 KB | **PASS** |
| scan + index throughput | ≥ 500 MB/s | 323 MB/s native / 252 MB/s WASM | **FAIL** |

`xmlspy bench` prints this FAIL itself rather than quietly rounding up. The 500 MB/s
figure in the Phase 0/1 design assumed a multi-core split (chunked parallel pre-scan with
a serial fix-up pass) on desktop-class hardware; neither the parallel scan nor that
hardware is in play here. On a single 2.6 GHz vCPU, 323 MB/s ≈ 8 bytes/cycle-ish is
roughly what a byte-at-a-time state machine with SWAR delimiter skipping should give.

Known routes to close the gap, in the order they are worth doing:

1. **Parallel chunked scan** (split at safe boundaries, merge indexes) — the design's
   original assumption; near-linear in cores, and the `Scanner` is already resumable, so
   the machinery exists.
2. **Skip the index when only well-formedness is asked for** — `wf` currently builds the
   full structural index (the CLI's `wf` measured 186 MB/s *with* indexing on the 256 MiB
   file; the index arrays are the dominant per-element cost).
3. Struct-of-arrays growth in one allocation instead of six `Vec::push` calls per element.

## Reproducing

~~~bash
cd rust
cargo run -p xmlspy-cli --release -- gen --size 64MiB --out /tmp/po64.xml
cargo run -p xmlspy-cli --release -- bench /tmp/po64.xml
cargo run -p xmlspy-cli --release -- search /tmp/po64.xml "Zürich"

cd ../XMLSpy
npm run build:wasm        # rebuild the module the browser runs
npm run test:parity       # 84 checks: Rust vs TypeScript, plus the real worker source
~~~

## Addendum — these numbers predate the mmap + parallel work

Everything above was measured with the CLI streaming 8 MiB `read()` chunks through a
sequential scan. Since then `rust/` gained `xmlspy-io` (mmap with a buffered fallback, `.xsi`
cache, write-ahead journal), `xmlspy-parallel` (split pass → threaded segments → exact merge)
and `xmlspy-rope`. **None of it has been compiled** — it was written in a sandbox with no Rust
toolchain — so no number in this report has been superseded yet, and none of the new code has
earned a place in it. What to expect when it is measured:

- **mmap** removes the kernel→user copy and the 8 MiB buffer from the index route. On a
  page-cache-resident corpus that is a small win; on a cold multi-GiB file it mostly changes
  *where* the waiting happens. RSS will look worse, not better, because mapped pages count as
  resident — the 75 MiB figure above is a streaming measurement and the two are not
  comparable. Read the `backend:` line `xmlspy bench` now prints before comparing anything.
- **The parallel route cannot scale linearly, by construction.** A sequential split pass of
  the real scanner finds the legal cut points first, so the total is `c·T + T/N` and the
  speed-up ceiling is `1/(c + 1/N)`. `xmlspy bench` prints the split/scan/merge breakdown so
  `c` is measurable instead of guessed. On this 2-vCPU sandbox an 8-thread number is
  meaningless (the gate correctly reports `FAIL` unless it is given ≥ 8 threads *and* a
  document large enough to split), so the ≥ 1.2 GB/s gate has to be run on real hardware.
- **The ≥ 500 MB/s single-thread gate is unchanged** and still fails here: the scanner's hot
  loop is the same code. mmap does not make the state machine faster.

Regenerate all of it, plus the new gates, with one command:

~~~bash
cd rust
./verify-phase1.sh                                   # fmt, clippy, tests, both bench routes,
                                                     # both gates, conformance — PASS/FAIL table
SIZE=1GiB THREADS=8 ./verify-phase1.sh               # a corpus big enough to split properly
cd ../XMLSpy && npm run test:conformance             # 41/41: mini suite vs the TS reference
~~~

Then replace the tables above with the new output and note the host — an 8-thread result from
a 2-vCPU container is not a result.
